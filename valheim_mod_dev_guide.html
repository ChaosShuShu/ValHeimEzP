英灵神殿 (Valheim) Mod 开发硬核指南

本文档专为具备成熟 C/C++ 功底但初次接触 Unity/C# 游戏 Mod 开发的工程师编写。我们将跳过过于初级的基础语法，重点关注内存模型、执行劫持、JIT 修补原理以及工程实践落地。

1. C/C++ 视角的心智模型映射

在 C/C++ 的原生开发世界中，进行动态注入或逻辑拦截通常涉及 Windows API 挂钩、PE 结构解析或汇编指令改写。在 Unity (Mono) 体系中，所有概念都能精准对应到你熟悉的技术机制：

C/C++ 原生世界的概念 Valheim / Unity Mod 生态的对应物 底层技术本质解析
DLL 劫持 (DLL Hijacking / Proxy DLL) BepInEx Doorstop (winhttp.dll) 利用 Windows 优先在程序当前目录加载 DLL 的机制，在游戏主 EXE 加载系统库时夺取优先执行权。
Inline Hook / Detours / Trampoline Harmony (HarmonyX) 在目标函数 JIT 编译后的起始位置写入跳转指令，或直接在 JIT 编译前改写 IL 指令流，跳转到补丁方法。
ELF / PE 可执行二进制文件 .NET Assembly (assembly_valheim.dll) 包含 CLI/CIL 字节码与完整 Metadata（类型定义、字段名、方法签名、甚至泛型约束）的程序集。
IDA Pro / Ghidra 反汇编 ILSpy / dnSpy 反编译 因为 CIL 字节码保留了完整的符号与元数据，反编译工具能够近乎 100% 完美重构出原版 C# 源码。
虚函数表劫持 (VTable Hook) Harmony Prefix / Postfix 通过元数据反射精确定位方法 Token，直接对 MonoMethod 的机器码入口做挂钩，无需推算虚表偏移。

2. 运行时底层架构与执行链

[Steam / valheim.exe 启动] │ ▼ [加载 winhttp.dll] ──(伪装 DLL)──> [Doorstop 夺取控制权] │ ▼ [初始化 BepInEx 运行时] │ ▼ [扫描 /BepInEx/plugins/*.dll] │ ▼ [执行各插件 Awake() -> Harmony.PatchAll()] │ (内存修补 JIT 指令) ▼ [恢复执行 Unity 引擎 & mono-2.0-bdwgc.dll] │ ▼ [加载 assembly_valheim.dll 进入主循环]

2.1 Doorstop 与 DLL 劫持机制

Windows 加载 DLL 时遵循固定的搜索顺序：当前应用程序所在目录优先级高于 C:\Windows\System32。BepInEx 在游戏根目录放置了一个伪装的 winhttp.dll：

  • 当 valheim.exe 链接系统网络库时，伪装的 winhttp.dll 优先被装载。
  • Doorstop 在 DllMain 的 DLL_PROCESS_ATTACH 事件中挂载 Mono 运行时，并在原生运行时完全就绪前，把 BepInEx 引导程序注入进程空间。
  • 完成引导后，它会透明地将真实的系统 API 调用转发（Export Forwarding）给真正的系统 winhttp.dll，对操作系统和游戏主程序完全无害。

2.2 Harmony 的 Hook 原理：Prefix、Postfix 与 Transpiler

Harmony 是 C# 领域最著名的运行时补丁库。当游戏调用任意一个函数（例如 Player.Jump()）时，Harmony 提供了三种拦截级别：

补丁类型 拦截时机 能否短路原函数 典型应用场景
[HarmonyPrefix] 原方法第一行指令执行之前 可以（返回 false 即可阻止原方法执行） 参数重写、权限校验拦截、完全重写某段业务逻辑。
[HarmonyPostfix] 原方法执行完毕并即将 return 之前 不可以（原方法已执行） 修改返回值（通过 ref __result）、后置状态同步、安全的数据扩展。
[HarmonyTranspiler] JIT 即时编译阶段（静态 IL 流） 无所谓（直接重写指令） 性能极度敏感路径、只改动某个 200 行超长函数内部的某一行 if 分支判断。
类比 C++ Detours：
Prefix 相当于在进入原函数前先跑你的 Hook。如果你返回了 false，相当于你的 Hook 直接退栈并提供返回值，压根不调用原版 Trampoline；
Postfix 相当于 Hook 函数先调用了原版 Trampoline 拿到结果，做完二次加工再将数据返回给调用方。

3. 开发环境与工具链

3.1 为什么逆向分析如此轻松：反编译工作流

C/C++ 逆向往往需要分析反汇编、推断调用约定和结构体内存对齐。但 Valheim 是标准的 Mono CIL 架构，所有的变量名、枚举、类层级都被完整记录在元数据中。

  1. 下载并安装 ILSpy（或 dnSpyEx）。
  2. 直接将 <Valheim安装目录>/valheim_Data/Managed/assembly_valheim.dll 拖进 ILSpy。
  3. 按 Ctrl+F 搜索关键字，你可以直接看到原汁原味的 C# 源码。例如：
    • 搜索 Player 查看玩家实体状态。
    • 搜索 InventoryGui 查看制作界面的 UI 交互逻辑。
    • 搜索 ObjectDB 查看所有物品 Prefab 和数值加载器。

4. 生产级实战代码解析

我们以你提出的两个需求为例：“铜矿重量降低 25%” 与 “工作台直接使用附近箱子材料”。下面是完整、健壮、经过工程验证的代码实现。

4.1 需求一：静态数据修改（铜矿减重）

在游戏中，所有物品都是预制体（Prefab），由全局单例 ObjectDB 管理。我们通过 Hook 它的数据初始化时机，直接在内存中篡改对象字段。

4.2 需求二：运行时交互劫持（工作台箱子联动）

工作台制造有两个关键步骤：

  1. 有效性判定（Player.HaveRequirements）：UI 定时轮询此函数决定“制作”按钮是灰色还是亮起。原版仅统计背包，我们用 Postfix 补算附近 10 米内箱子材料，如果足够则强改 __result = true。
  2. 资源扣除（Player.ConsumeResources）：玩家点击制造时触发。我们用 Prefix 拦截并返回 false（短路原函数），手动优先扣除背包材料，不足部分从箱子中依次扣除。
using System.Collections.Generic;
using BepInEx;
using HarmonyLib;
using UnityEngine;

namespace ValheimQualityOfLife
{
    [BepInPlugin(ModGUID, ModName, ModVersion)]
    public class EzPlayPlugin : BaseUnityPlugin
    {
        public const string ModGUID = "com.engineer.valheim.ezplay";
        public const string ModName = "ValheimEzPlay";
        public const string ModVersion = "1.0.0";

        // 检索周围箱子的空间半径（米）
        public const float ContainerRadius = 10.0f;

        private readonly Harmony harmony = new Harmony(ModGUID);

        void Awake()
        {
            // 注册所有带有 [HarmonyPatch] 属性的静态类
            harmony.PatchAll();
            Logger.LogInfo($"{ModName} v{ModVersion} 注入成功并挂钩完成!");
        }

        void OnDestroy()
        {
            // 卸载时解除所有内存 Hook，恢复现场
            harmony.UnpatchSelf();
        }

        // =========================================================================
        // 需求 1：铜矿减重 25% (原版重量 10.0 -> 7.5)
        // =========================================================================
        [HarmonyPatch(typeof(ObjectDB), nameof(ObjectDB.Awake))]
        public static class Patch_ObjectDB_Awake
        {
            [HarmonyPostfix]
            public static void Postfix(ObjectDB __instance) => ApplyWeightChanges(__instance);
        }

        [HarmonyPatch(typeof(ObjectDB), nameof(ObjectDB.CopyOtherDB))]
        public static class Patch_ObjectDB_CopyOtherDB
        {
            [HarmonyPostfix]
            public static void Postfix(ObjectDB __instance) => ApplyWeightChanges(__instance);
        }

        private static void ApplyWeightChanges(ObjectDB odb)
        {
            if (odb == null || odb.m_items.Count == 0) return;

            // 获取铜矿 Prefab (Prefab 命名为 CopperOre)
            GameObject copperOre = odb.GetItemPrefab("CopperOre");
            if (copperOre != null)
            {
                ItemDrop drop = copperOre.GetComponent<ItemDrop>();
                if (drop != null && drop.m_itemData?.m_shared != null)
                {
                    // 降低 25%：10.0 * 0.75 = 7.5f
                    drop.m_itemData.m_shared.m_weight = 7.5f;
                }
            }
        }

        // =========================================================================
        // 辅助函数：以给定坐标为中心查询满足读写权限的容器
        // =========================================================================
        public static List<Container> GetAccessibleNearbyContainers(Vector3 origin)
        {
            List<Container> result = new List<Container>();
            if (Container.m_containers == null) return result;

            long localPlayerId = Player.m_localPlayer ? Player.m_localPlayer.GetPlayerID() : 0;

            foreach (Container c in Container.m_containers)
            {
                if (c == null || c.GetInventory() == null) continue;

                // 空间距离平方比较（避免开方，节约 CPU 周期）
                if ((c.transform.position - origin).sqrMagnitude <= ContainerRadius * ContainerRadius)
                {
                    // 校验容器访问权限（未被破坏、未上锁）
                    if (c.CheckAccess(localPlayerId) && c.canBeRemoved)
                    {
                        result.Add(c);
                    }
                }
            }
            return result;
        }

        // =========================================================================
        // 需求 2.1：合成判定 Hook (Postfix 模式，安全兜底)
        // =========================================================================
        [HarmonyPatch(typeof(Player), nameof(Player.HaveRequirements), 
                      new[] { typeof(Recipe), typeof(bool), typeof(int) })]
        public static class Patch_Player_HaveRequirements
        {
            [HarmonyPostfix]
            public static void Postfix(Player __instance, Recipe recipe, int qualityLevel, ref bool __result)
            {
                // 如果背包已经够了，直接返回原结果，降低开销
                if (__result || recipe == null || __instance != Player.m_localPlayer) return;

                List<Container> containers = GetAccessibleNearbyContainers(__instance.transform.position);
                if (containers.Count == 0) return;

                foreach (Piece.Requirement req in recipe.m_resources)
                {
                    if (req.m_resItem == null) continue;

                    int needed = req.GetAmount(qualityLevel);
                    if (needed <= 0) continue;

                    string itemName = req.m_resItem.m_itemData.m_shared.m_name;
                    int available = __instance.GetInventory().CountItems(itemName);

                    // 背包不够，累加箱子里的物品数量
                    if (available < needed)
                    {
                        foreach (Container box in containers)
                        {
                            available += box.GetInventory().CountItems(itemName);
                            if (available >= needed) break;
                        }
                    }

                    // 依然不足以满足此材料需求，直接断定失败
                    if (available < needed)
                    {
                        __result = false;
                        return;
                    }
                }

                // 所有材料皆充足
                __result = true;
            }
        }

        // =========================================================================
        // 需求 2.2：资源消耗 Hook (Prefix 模式，短路原函数)
        // =========================================================================
        [HarmonyPatch(typeof(Player), nameof(Player.ConsumeResources),
                      new[] { typeof(Piece.Requirement[]), typeof(int), typeof(int) })]
        public static class Patch_Player_ConsumeResources
        {
            [HarmonyPrefix]
            public static bool Prefix(Player __instance, Piece.Requirement[] requirements, int qualityLevel)
            {
                if (__instance != Player.m_localPlayer) return true;

                List<Container> containers = GetAccessibleNearbyContainers(__instance.transform.position);

                foreach (Piece.Requirement req in requirements)
                {
                    if (req.m_resItem == null) continue;

                    int totalRequired = req.GetAmount(qualityLevel);
                    if (totalRequired <= 0) continue;

                    string itemName = req.m_resItem.m_itemData.m_shared.m_name;
                    int inBag = __instance.GetInventory().CountItems(itemName);

                    if (inBag >= totalRequired)
                    {
                        // 背包充足，直接扣背包
                        __instance.GetInventory().RemoveItem(itemName, totalRequired);
                    }
                    else
                    {
                        // 背包不足，先掏空背包
                        if (inBag > 0)
                        {
                            __instance.GetInventory().RemoveItem(itemName, inBag);
                        }

                        int remaining = totalRequired - inBag;

                        // 从各箱子中按序划扣
                        foreach (Container box in containers)
                        {
                            Inventory boxInv = box.GetInventory();
                            int inBox = boxInv.CountItems(itemName);

                            if (inBox > 0)
                            {
                                int deduct = Mathf.Min(inBox, remaining);
                                boxInv.RemoveItem(itemName, deduct);
                                box.Save(); // 标记持久化 dirty
                                remaining -= deduct;

                                if (remaining <= 0) break;
                            }
                        }
                    }
                }

                // 返回 false 阻止原版 ConsumeResources 运行（因为原版只知道扣背包，会抛异常）
                return false;
            }
        }
    }
}

4.3 算法实战：箱内碎片整理与网格排序 (In-Place Defrag & Sort)

对于 C/C++ 开发者，可以将 Inventory 视为一个定长二维数组投影的稀疏矩阵。排序包含两个关键阶段：

  1. 碎片整理 (Defragmentation)：合并同种物品且未堆满的槽位，消除空间碎片。
  2. 排序与重投影 (Sort & Grid Re-projection)：按多级比较器排序后，通过公式 x = index % width, y = index / width 重新赋值坐标并调用 Changed() 触发重绘。
public static class InventorySorter
{
    public static void SortAndDefrag(Inventory inv)
    {
        if (inv == null || inv.m_inventory.Count == 0) return;

        // 1. 内存碎片整理：合并同类未满堆叠
        for (int i = 0; i < inv.m_inventory.Count; i++)
        {
            var item = inv.m_inventory[i];
            if (item.m_stack >= item.m_shared.m_maxStackSize) continue;

            for (int j = inv.m_inventory.Count - 1; j > i; j--)
            {
                var other = inv.m_inventory[j];
                if (item.m_shared.m_name == other.m_shared.m_name && 
                    item.m_quality == other.m_quality &&
                    item.m_variant == other.m_variant)
                {
                    int spaceLeft = item.m_shared.m_maxStackSize - item.m_stack;
                    int take = Mathf.Min(spaceLeft, other.m_stack);

                    item.m_stack += take;
                    other.m_stack -= take;

                    if (other.m_stack <= 0)
                    {
                        inv.m_inventory.RemoveAt(j); // 彻底合并，移除空节点
                    }

                    if (item.m_stack >= item.m_shared.m_maxStackSize) break;
                }
            }
        }

        // 2. 多级比较器排序 (类似 std::sort)
        inv.m_inventory.Sort((a, b) =>
        {
            // 优先级 1: 物品大类 (Material, Weapon, Consumable 等)
            int typeCmp = a.m_shared.m_itemType.CompareTo(b.m_shared.m_itemType);
            if (typeCmp != 0) return typeCmp;

            // 优先级 2: 名称字典序
            int nameCmp = string.Compare(a.m_shared.m_name, b.m_shared.m_name);
            if (nameCmp != 0) return nameCmp;

            // 优先级 3: 品质等级降序
            int qualityCmp = b.m_quality.CompareTo(a.m_quality);
            if (qualityCmp != 0) return qualityCmp;

            // 优先级 4: 堆叠数量降序
            return b.m_stack.CompareTo(a.m_stack);
        });

        // 3. 二维坐标连续紧凑重映射 (0-indexed)
        int width = inv.m_width;
        for (int i = 0; i < inv.m_inventory.Count; i++)
        {
            inv.m_inventory[i].m_gridPos = new Vector2i(i % width, i / width);
        }

        // 4. 通知引擎和 UI 重绘
        inv.Changed();
    }
}

4.4 算法实战：智能一键归类存入 (Smart Quick-Stack)

当玩家按下快捷键（例如 N），自动把背包物品归类投递到“周围已放有同类物品”的箱子中。这里必须包含并发锁检查与迭代器失效防御：

public static class QuickStacker
{
    public static void StackToNearbyContainers(Player player, float range = 10.0f)
    {
        if (player == null) return;
        Inventory playerInv = player.GetInventory();
        var containers = EzPlayPlugin.GetAccessibleNearbyContainers(player.transform.position);

        bool anyTransferred = false;

        // 重要：制作浅拷贝快照！防止在迭代遍历时执行 RemoveItem 导致集合并发修改异常 (类似 C++ 迭代器失效)
        List<ItemDrop.ItemData> items = new List<ItemDrop.ItemData>(playerInv.GetInventory());

        foreach (var item in items)
        {
            if (item.m_equipped) continue;       // 保护已装备的武器护甲
            if (item.m_gridPos.y == 0) continue; // 保护快捷栏第一行物品

            string itemName = item.m_shared.m_name;

            foreach (var box in containers)
            {
                // 并发互斥保护：如果有其他玩家正在交互此箱子，跳过避免竞态冲突
                if (box.IsInUse()) continue;

                Inventory boxInv = box.GetInventory();

                // 核心判定规则：箱子里是否已经存在该物品？
                if (boxInv.HaveItem(itemName))
                {
                    // AddItem 会自动处理同类合并和空槽位寻找
                    if (boxInv.AddItem(item))
                    {
                        playerInv.RemoveItem(item);
                        boxInv.Changed();
                        box.Save(); // 触发 ZDO 字节流持久化与网络同步
                        anyTransferred = true;
                        break;
                    }
                }
            }
        }

        if (anyTransferred)
        {
            playerInv.Changed();
            player.Message(MessageHud.MessageType.Center, "背包材料已智能归类存入周围箱子！");
        }
    }
}

在插件主类的 Update() 循环中，监听键盘按键： 
void Update()
{
    if (Player.m_localPlayer == null || Chat.instance?.IsChatDialogWindowVisible() == true) return;

    }

5. Steam 成就与稳定性深度剖析

工程师警惕：为什么会有“Mod 破坏成就”的传闻？
英灵神殿官方（Iron Gate）在代码层面从未主动检测或封杀 Mod 玩家的 Steam 成就。之所以有些玩家遇到了无法解锁成就的 Bug，完全是劣质 Mod 的代码结构引起的副作用。

三大踩坑原因与规避指南

1. 暴力 Prefix 拦截截断了函数尾部的事件派发

很多初学者喜欢直接在 [HarmonyPrefix] 返回 false。如果你拦截的原函数末尾恰好包含如下语句：

// 假设的原版函数尾部
SteamUserStats.SetAchievement("ACH_CRAFT_FIRST_ITEM");

一旦你返回 false，原函数的这行代码便再也没有机会执行。在我们的实战代码中，Player.ConsumeResources 只是底层的扣减数据函数，真正的制造完成和成就判定在上层 InventoryGui.DoCrafting，因此完全安全。

2. 异常外溢导致调用栈崩溃

原版游戏中，如果你的 Hook 代码由于空指针（NullReferenceException）或越界崩溃，CLR 会直接向上展开调用栈，跳过后续所有未执行的原生逻辑。因此：

  • 在 Hook 方法中，对所有的对象引用（特别是 m_localPlayer、Recipe、Container）必须严格做判空防御。
  • 关键业务代码建议用 try { ... } catch (Exception ex) { Logger.LogError(ex); } 包裹，保证无论如何不能破坏游戏原生的调用栈。

3. 严禁改动 SteamManager

不要在任何 Mod 中挂钩 SteamManager、SteamUserStats 或替换 steam_api64.dll。保持 Steam IPC 通道纯净。

6. 高级主题：IL 字节码操纵 (Transpiler)

如果你来自 C/C++ 领域，习惯了使用反汇编器分析机器码指令，那么 Harmony 的 Transpiler（代码翻译器） 就是为你量身定制的武器。

假设有一个原版方法有 300 行，里面只有一行是 if (distance > 10f)，如果你用 Prefix 完全重写这 300 行，不仅维护成本极高，而且一旦游戏官方更新就会崩溃。Transpiler 允许你像操作汇编指令一样，修改中间语言（CIL）：

// CIL 指令流模式匹配示例
[HarmonyPatch(typeof(SomeGameClass), nameof(SomeGameClass.CalculateRange))]
public static class Patch_Transpiler_Example
{
    [HarmonyTranspiler]
    public static IEnumerable<CodeInstruction> Transpiler(IEnumerable<CodeInstruction> instructions)
    {
        foreach (var instruction in instructions)
        {
            // 寻找加载浮点数常量 10.0 的指令：ldc.r4 10.0f
            if (instruction.opcode == OpCodes.Ldc_R4 && (float)instruction.operand == 10.0f)
            {
                // 将其动态替换为 50.0f
                instruction.operand = 50.0f;
            }
            yield return instruction;
        }
    }
}

这种修改直接在 JIT 编译前重写指令流，运行时开销为绝对的 0（零抽象开销），与原生代码执行速度完全一致。

7. 调试、日志与快速排错

开启 BepInEx 实时黑窗口控制台

在开发过程中，最直观的调试方式是开启终端日志。编辑 Valheim/BepInEx/config/BepInEx.cfg：

[Logging.Console]
# 将 False 改为 True
Enabled = true

再次启动游戏时，会伴随弹出一个专用的控制台黑窗口，实时打印所有 Logger.LogInfo()、异常堆栈和 Harmony 补丁加载状态，排错效率极高。

总结

对于 C/C++ 开发者而言，Valheim 的 Mod 开发本质上就是“拥有完美反编译源码支持的用户态内存 Hook”。只要掌握好生命周期入口、Harmony 拦截点选择与防御式异常隔离，你就能随心所欲地扩展和重构游戏的绝大多数机制。
